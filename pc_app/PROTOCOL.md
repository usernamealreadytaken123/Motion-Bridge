# Android → ПК: UDP JSON v2

Одна UTF-8 JSON-дейтаграмма = один snapshot. Частота отправки: 50 Гц.
Старые верхнеуровневые поля сохранены. Неизвестные поля расширений игнорируются
при интерпретации и остаются в записи. Протокол без `protocol_version` считается v1.
Неизвестная версия, тип пакета, повторяющиеся ключи, неконечные числа и неверные
типы данных отвергаются. Монотонные timestamps и sequence — целые int64 >= 0.

| Поле | Значение |
|---|---|
| `protocol_version` | `2` |
| `packet_type` | `telemetry` |
| `session_id` | Новый UUID на каждый старт UDP; не является аппаратным ID |
| `sequence` | Номер дейтаграммы внутри сессии, начинается с 0 |
| `timestamp` | Unix time телефона, секунды; для календаря, не для вычисления Δt |
| `device_timestamp_ns` | `elapsedRealtimeNanos()` перед отправкой |
| `sensor_timestamps_ns` | Исходное время последнего события каждого сенсора; 0 — ещё нет измерения |
| `quaternion` | Android rotation-vector quaternion `{w,x,y,z}`, без визуального центрирования UI |
| `gyroscope` | Последнее событие гироскопа, `{x,y,z}`, рад/с, оси Android-устройства |
| `linear_acceleration` | Android `TYPE_LINEAR_ACCELERATION`, м/с²; это не сырой акселерометр |
| `height_above_surface_m` | Прежнее поле фиксированной высоты из TrackingConfiguration |
| `planar_odometry` | `null`, если одометрия ещё не создавалась; иначе блок ниже |

Внутри `sensor_timestamps_ns`: `quaternion`, `gyroscope`, `linear_acceleration`.
Эти три измерения обычно имеют разные времена. Пакет является snapshot, а не
синхронным IMU-сэмплом. Сырые измерения, включая гравитацию, потребуются на этапе VIO.

| Поле `planar_odometry` | Значение |
|---|---|
| `epoch` | Увеличивается при старте/сбросе позиции; новая система отсчёта |
| `timestamp_ns` | Timestamp обработанного кадра камеры, 0 до первого кадра |
| `status` | STOPPED, STARTING_CAMERA, INITIALIZING, TRACKING, DEGRADED, LOST, ERROR |
| `camera_active` | Состояние камеры по контроллеру |
| `x_m`, `y_m` | Абсолютная накопленная 2D-позиция, метры |
| `heading_rad` | Накопленный поворот в плоскости, радианы |
| `delta_x_m`, `delta_y_m` | Изменение на обработанном кадре; не суммировать повторные timestamps |
| `surface_distance_m` | Расстояние, реально использованное камерным алгоритмом |
| `tracked_points`, `inliers` | Число соответствий и принятых точек |
| `inlier_ratio` | Доля от 0 до 1; не вероятностная оценка точности позиции |
| `image_scale` | Относительный масштаб между кадрами |
| `intrinsics_approximate` | Параметры камеры приблизительные по текущему контроллеру |

Ключ траектории: `(sender, session_id, epoch)`. Идентификатор кадра в пределах
траектории — `timestamp_ns`. Сброс или повторный старт одометрии разрывает траекторию.
При STOPPED/DEGRADED/ERROR координаты могут быть последним сохранённым результатом.
Последовательность новых UDP-пакетов не означает последовательность новых кадров.

2D-координаты заданы в плоскости кадра при сбросе: начальный X направлен вправо,
Y — вниз в ориентированном изображении. Они не совпадают автоматически с мировой
системой rotation vector или осями будущей 3D-сцены. Z не измеряется этим алгоритмом.

В прежнем режиме синхронизация времени камеры с IMU не требуется. Режим компенсации
наклона разрешён только при `SENSOR_INFO_TIMESTAMP_SOURCE_REALTIME`: Android гарантирует
общую шкалу с датчиками. Используется интерполяция исходных quaternion вокруг времени
кадра; аппаратная задержка фильтра ориентации и rolling shutter отдельно не откалиброваны.
Часы ПК и Android не синхронизированы. Нельзя вычитать их монотонные времена или
заявлять сетевую задержку по разнице календарных часов.

### Расширение компенсации наклона

Начиная с Android `1.15-lidar`, при выборе iPhone дополнительно передаются
поля `height_source: "IPHONE_LIDAR"`, `height_valid` (bool), `lidar_depth_m`,
`lidar_age_ms`, `lidar_rtt_ms`, `lidar_time_s` (число или null).
`surface_distance_m` — вертикальная высота Android-камеры, а не глубина вдоль
оптической оси. При `height_valid=false` это последнее значение/начальная заглушка,
не новая высота; XY не интегрируется без валидной пары кадров.
Флаг относится к timestamp кадра, а не к текущему времени приёма UDP.
`lidar_depth_m` и `lidar_time_s` интерполированы для кадра; это не сырой пакет iPhone.
`lidar_age_ms` — интервал от левой границы LiDAR-пары до кадра в приближённой шкале,
не измерение полной аппаратной задержки. `lidar_rtt_ms` — максимум HTTP RTT пары.
Источник времени LiDAR — эксперимент phyphox, Android camera timestamp задержан
относительно отправки примерно на 200 мс для интерполяции. Аппаратной синхронизации нет.
Верхнеуровневое `height_above_surface_m` осталось прежним полем совместимости.
Старые записи без новых полей работают как раньше; JSONL сохраняет расширение.
Настройка связки и ограничения: [LIDAR_ODOMETRY.md](../LIDAR_ODOMETRY.md).

При `planar_odometry.mode = "TILT_COMPENSATED"` X/Y находятся в **горизонтальной**
плоскости: X — проекция направления вправо в начальном кадре, Y — перпендикулярное
направление, согласованное с направлением вниз начального изображения. Начальная
система фиксируется на первом кадре с пригодной ориентацией. `heading_rad` — текущий
поворот относительно этой базы, не интеграл поворотов изображения.
`surface_distance_m` — заданная вертикальная высота оптического центра камеры.
`image_scale = 1` — поле совместимости; масштаб изображения в этом режиме не оценивается.

Дополнительные поля: `tilt_deg` — угол оптической оси от вертикали вниз,
`orientation_gap_ms` — интервал между IMU-ориентациями, использованными для интерполяции
(не сетевая задержка), `ground_residual_m` — RMS расхождения принятых перемещений точек
(не абсолютная ошибка позиции). Значения могут быть `null`, если ещё нет оценки.
`intrinsics_approximate = false` означает наличие параметров в метаданных, а не полную
проверку калибровки объектива, его дисторсии и монтажа относительно IMU.

При отсутствии `mode` используется прежняя семантика. Существующий ПК-клиент принимает
новые пакеты и сохраняет дополнительные поля, но пока не отображает их отдельными карточками.

## Запись JSONL

Один файл — один запуск ПК-приёмника. Каждая строка содержит:

- `record_version: 1`;
- `pc_receive_monotonic_ns` и `pc_receive_unix_ns`;
- `sender: [IPv4, port]`;
- `raw_base64`: точные байты дейтаграммы, включая повреждённые;
- `payload`: разобранный объект либо null;
- `error`: причина отказа либо null;
- `sequence_result`: new / reordered / duplicate / too_late для корректных пакетов.

Запись идёт в отдельном потоке с ограниченной очередью. Переполнение или ошибка
диска завершают приём с ошибкой, чтобы не выдавать неполную запись за полную.
Размер UDP ограничен 65507 байт; обычный v2 пакет укладывается в 1400 байт
(проверяется на общем образце). Кадры и массивы кейпоинтов сюда не включаются.

## Независимый TCP-протокол исходных данных MVO1

Android `1.17-h264`, TCP-порт по умолчанию 5006. Старый UDP v1/v2 не изменён.
Одно TCP-соединение — одна сессия, один телефон. Формат каждого сообщения:

- 4 байта ASCII `MVO1`;
- uint32 big-endian: длина UTF-8 JSON-заголовка, от 1 до 65536 байт;
- uint32 big-endian: длина бинарного payload, от 0 до 1280×960 байт;
- JSON-объект, затем payload без разделителей/дополнения.

Первый заголовок: protocol 1 + encoding `gray8` для RAW либо protocol 2 + encoding
`h264` для сжатого потока. Например:
`{"type":"hello","protocol":2,"encoding":"h264","session":"UUID","token":"8-hex"}`.
ПК подтверждает верный код единственным байтом `0x01`. При неверном коде закрывает
соединение и ждёт следующее. Код не сохраняется в `.mvo`; шифрования нет.

Остальные сообщения:

- `sensors`: `watermark_ns` (целое >0), `samples` (до 256 массивов):
  `["q",timestamp_ns,w,x,y,z]`, `["gyro",timestamp_ns,x,y,z]`,
  `["accel",timestamp_ns,x,y,z]`, `["linear",timestamp_ns,x,y,z]`.
  Порядок quaternion wxyz; единицы — рад/с и м/с². `accel` включает гравитацию.
  Пустой batch служит heartbeat. Timestamp — исходный timestamp события Sensor API.
  Watermark — монотонное время Android после выгрузки уже полученных событий/кадра;
  при разбиении очереди он продвигается только после всех её частей.
  Это не гарантия нулевой аппаратной задержки датчиков.
- `frame`: `seq`, `timestamp_ns`, `width`, `height`, `rotation` (0/90/180/270),
  `sensor_orientation` (те же углы или null), `realtime`, `back_camera`, `approximate`
  (строгие bool), `intrinsics:[fx,fy,cx,cy]`, `dropped` (число замен в mailbox).
  Payload — ровно width×height яркостей uint8 GRAY8, без row padding.
  Изображение ещё не повёрнуто; intrinsics соответствуют этим сырым размерам.
  Размер каждой стороны 16–1280, произведение ≤1280×960. Seq увеличивается для
  выбранных к передаче кадров; пропуски показывают замену кадров, не все потери CameraX.
- `video_config` (protocol 2): codec `h264`, width/height, fps и bitrate. Бинарный
  payload содержит SPS/PPS и передаётся до первого access unit и после перезапуска кодека.
- `video_packet` (protocol 2): те же метаданные камеры, что у `frame`, плюс `pts_us`
  и `keyframe`. Бинарный payload — один H.264 access unit. PTS получен из исходного
  CameraX timestamp; B-кадры отключены. Отбрасывать такой пакет после кодирования нельзя.
- `lidar`: `ok:false` при ошибке/остановке источника; при `ok:true` — `session`,
  `measuring`, `depth_m`, `time_s`, `requested_ns`, `received_ns`, `mount:[x,y,z]`.
  В паузе depth/time могут быть null. Depth — центральная осевая глубина phyphox;
  mount — вектор от LiDAR до Android-камеры в осях устройства Android, метры.
  Время эксперимента iPhone в секундах; requested/received — наносекунды Android.

Все измеренные числа конечны; JSON с повторными ключами отклоняется. Бинарный
payload допустим у `frame`, `video_config` и `video_packet`. Часы ПК не участвуют в компенсации наклона/высоты.
Запись `capture.mvo` использует те же конверты в том же порядке, но без pairing token.
`manifest.json` хранит настройки и состояние завершения; `results.jsonl` — новый
формат результатов PC, не оболочки UDP record_version=1. Подробная семантика,
синхронизация и ограничения: [PC_ODOMETRY.md](../PC_ODOMETRY.md).
