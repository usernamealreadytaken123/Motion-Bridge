# Motion Viewer — 3D-ориентация, телеметрия и воспроизведение

ПК-приложение для Android UDP v1/v2: показатели датчиков, графики гироскопа и
линейного ускорения, 3D-модель телефона, 2D-траектория, контроль связи, запись и replay JSONL. Консольные
команды первого этапа сохранены. Android и ПК остаются отдельными приложениями
в одном репозитории; `pc_app` не входит в APK.

## Запуск готового приложения

Откройте **`pc_app/dist/MotionViewer.exe`** двойным щелчком. Windows x64, Python
и другие библиотеки отдельно устанавливать не нужно. Это один автономный файл.
Настройки, журнал и новые записи по умолчанию: `%LOCALAPPDATA%/MotionViewer/`.

Вкладка «3D-ориентация» показывает поворот телефона. «Открыть JSONL…» включает
воспроизведение телеметрии с паузой, перемоткой и скоростью 0.25×–8×.
Подробности, ограничения, расположение данных и сборка: **[DESKTOP.md](DESKTOP.md)**.

## Запуск из исходников

Для закреплённых GUI-зависимостей нужен **Python 3.12–3.14**; проверено на Python 3.12.
Консольный режим по-прежнему работает на Python 3.10+ без дополнительных пакетов.
Из корня проекта в PowerShell:

```powershell
python -m venv pc_app/.venv
.\pc_app\.venv\Scripts\python.exe -m pip install -r pc_app/requirements-gui.txt
.\pc_app\.venv\Scripts\python.exe -m pc_app.motion_viewer gui
```

Окружение на текущем компьютере уже создано; первые две команды повторять не нужно.
Можно также открыть `pc_app/run_viewer.cmd` двойным щелчком. Активация виртуального
окружения и изменение политики PowerShell не требуются.

1. Оставьте адрес прослушивания `0.0.0.0` и порт `5005`.
2. При необходимости выберите папку записей; запись включена по умолчанию.
3. Нажмите **«Начать приём»**, затем запустите UDP на Android. На телефоне укажите
   действительный IPv4 компьютера, не `0.0.0.0`. Устройства должны быть в одной сети.
4. Запустите камерную одометрию: появятся координаты и траектория.
5. **«Остановить»** завершает приём и сохраняет очередь записи. Закрытие окна
   выполняет ту же операцию. Для следующего запуска создаётся новый файл.

### Что показывает окно

- Quaternion `(w, x, y, z)`, гироскоп в рад/с и линейное ускорение в м/с².
- Графики XYZ: до 1500 последних измерений, видимый интервал — до 30 секунд.
  Время — относительное время приёма ПК; это не синхронизированное время IMU.
  Повторные snapshot одного измерения не добавляются в график; timestamp 0 пропускается.
- Траектория: последние 5000 точек и разрывов; X направлен вправо, Y вниз, как
  в системе Android при сбросе. Оба масштаба одинаковы. Прокрутка мышью меняет
  масштаб; кнопка `A` внутри графика возвращает автомасштаб.
- Новая `epoch` очищает траекторию выбранной сессии. Потери tracking и долгие
  паузы разрывают линию. Абсолютные X/Y передаются с Android, повторного интегрирования нет.
- Автовыбор последнего активного потока или ручной выбор по отправителю и session ID.
  При одновременной передаче с нескольких источников удобнее выбрать поток вручную.
- Отдельно показаны отсутствие UDP, отсутствие обновлений кадров и состояние одометрии.
  Оранжевая точка — последнее сохранённое положение, а не подтверждение текущего tracking.
- **«Очистить графики»** меняет только отображение на ПК, не сбрасывает Android и
  не удаляет данные записи. Новый приём начинает историю интерфейса заново.

Приём и запись выполняются в фоновых потоках, интерфейс обновляется 10 раз/с.
История ограничена 16 потоками; самые давно обновлявшиеся вытесняются. Очередь
экрана ограничена 2048 событиями. Если интерфейс не успевает, счётчик предупреждает
о пропусках только отображения; запись продолжает получать исходные дейтаграммы.
Ошибка самой записи останавливает приём с сообщением, а не скрывается.

Графики — диагностика текущих snapshot, а не поток сырых IMU для VIO. Видео с камеры,
3D-перемещение и вычисление новой одометрии на ПК не добавлены.

## Консольный запуск с телефоном

В PowerShell, из корня проекта:

```powershell
Set-Location 'C:\Users\mrart\AndroidStudioProjects\MyApplication'
python -m pc_app.motion_viewer listen --record pc_app/recordings/phone-test-01.jsonl
```

1. Установите собранный `app/build/outputs/apk/debug/app-debug.apk` на Android.
2. Подключите ПК и телефон к одной Wi-Fi сети.
3. Найдите IPv4 компьютера в `ipconfig` и укажите его в Android-приложении,
   порт — `5005`. `0.0.0.0` — адрес прослушивания, его не вводят на телефоне.
4. Запустите UDP на телефоне. На ПК появятся `RECEIVING`, quaternion,
   гироскоп, линейное ускорение и счётчики.
5. Запустите камерную одометрию на телефоне. Появятся `camera=TRACKING`,
   `x`, `y`, число inliers и `epoch`. Значения должны соответствовать экрану Android.
6. Нажмите сброс 2D-позиции: `epoch` увеличится, координаты обнулятся.
7. Остановите UDP: через две секунды на ПК появится `STALE`.
8. Запустите UDP снова: появится новая `session`, sequence начнётся с нуля.
9. Завершите приём сочетанием Ctrl+C; очередь записи будет сохранена.

Для ограниченного по времени опыта добавьте `--duration 30`. Чтобы не записывать
данные, уберите `--record`. У каждого опыта должно быть новое имя файла:
существующие записи не перезаписываются.

Если Windows покажет запрос межсетевого экрана, разрешите Python для частной сети.
Если данных нет, проверьте адрес ПК, порт, профиль сети и изоляцию клиентов на роутере.
При ошибке занятого порта остановите старый `udp_receiver.py` / `udp_probe.py`,
который слушает тот же порт. Приложение не меняет настройки firewall автоматически.
Используйте доверенную локальную сеть: текущий UDP-протокол не имеет шифрования
и аутентификации отправителя. Не открывайте этот порт в интернет.

## Проверка без телефона

В первом терминале:

```powershell
python -m pc_app.motion_viewer listen --host 127.0.0.1 --record pc_app/recordings/simulation-01.jsonl
```

Во втором терминале из того же корня проекта:

```powershell
python -m pc_app.motion_viewer simulate --duration 10 --rate 50 --drop-every 10 --duplicate-every 15
```

Симулятор отправляет явно помеченную `sim-…` сессию, синтетическую круговую
траекторию, пропуски и дубли. Это проверка транспорта, не проверка точности одометрии.
После Ctrl+C в приёмнике проверьте файл:

```powershell
python -m pc_app.motion_viewer inspect pc_app/recordings/simulation-01.jsonl
```

`inspect` сверяет каждую сохранённую дейтаграмму с разобранным пакетом и сообщает
номер повреждённой строки. Для воспроизведения откройте этот JSONL в графическом окне.

## Что означают счётчики

- `pps`: частота полученных корректных пакетов за последние три секунды, включая дубли.
- `pending`: пропуски sequence внутри окна последних 256 номеров; могут прийти позже.
- `missing`: пропуски, вышедшие из этого окна. Это потери по выбранному окну,
  а не доказательство, что пакет никогда не придёт.
- `dup`: повторы в пределах окна; `reordered`: заполнившие пропуск пакеты.
- `old`: номера старее окна; для них повтор и очень позднюю доставку уже не различаем.
- `age`: время с последнего корректного пакета по монотонным часам ПК, не сетевая задержка.
- `invalid`: отвергнутые дейтаграммы; при записи их исходные байты тоже сохраняются.

Пакеты до первого принятого sequence и потери в самом конце передачи не могут быть
определены без дополнительных сообщений. У v1 нет session ID: перезапуск Android
неотличим от позднего старого пакета; для отдельного v1 опыта перезапускайте приёмник.
В v2 статистика разделена по адресу отправителя, UDP-порту и session ID.

Новая позиция на ПК берётся из абсолютных `x_m/y_m`. `delta_x_m/delta_y_m` могут
повторяться в нескольких UDP-пакетах одного кадра; суммировать их на каждом пакете нельзя.
`TRACKING` сообщает состояние последнего обработанного кадра. UDP может продолжаться
при остановившейся камере: GUI отдельно предупреждает, если camera timestamp
не обновляется более двух секунд. Численные значения при этом остаются последними полученными.

## Автоматические проверки

```powershell
python -m unittest discover -s pc_app/tests -v
.\pc_app\.venv\Scripts\python.exe -m unittest discover -s pc_app/tests -v
.\gradlew.bat testDebugUnitTest assembleDebug lintDebug
```

Общий файл `app/src/test/resources/telemetry_v2.json` проверяется Kotlin-тестом
сериализатора и Python-парсером. Тесты ПК включают реальные loopback UDP-сокеты,
отдельный процесс симулятора, пропуски, перестановки, дубли, разные сессии,
сброс одометрии, повреждённый JSON и сохранение исходных байтов.

Тесты Qt запускаются без видимого окна и автоматически пропускаются, если GUI-зависимости
не установлены. Запуск через `.venv` выполняет полный набор. Дополнительно проверяются
обновление графиков через UDP, остановка/повторный старт, завершение записи, конфликт
порта, дедупликация кадров, устаревание камеры, границы истории и медленный интерфейс.

Воспроизводимый рендер окна с синтетическими UDP-данными:

```powershell
.\pc_app\.venv\Scripts\python.exe -m pc_app.tests.render_preview
```

Создаёт `pc_app/artifacts/gui-preview.png`; не использует телефон и не подтверждает
точность одометрии. Для обычного оконного теста запустите GUI, нажмите «Начать приём»
и во втором терминале выполните команду `simulate` из раздела выше.

## Дальнейшие этапы

1. Готово: UDP v1/v2, типизированный разбор, статистика, JSONL, тесты.
2. Готово: PySide6-окно, численные данные, графики, 2D-траектория.
3. Готово: 3D-ориентация телефона, визуальная нулевая база.
4. Готово: replay телеметрии, пауза, перемотка, скорости 0.25×–8×.
5. Готово: Windows `.exe`, сохранение настроек, журнал ошибок.
6. Далее при необходимости: экспорт CSV, поток сырых IMU/кейпоинтов и backend VIO.

Этот этап передаёт снимки данных на 50 Гц. Это ещё не поток сырых IMU и не 3D VIO.
Погрешность текущей камерной одометрии оценивается отдельно на реальном устройстве.

Технические справочники: [Qt: потоки и GUI](https://doc.qt.io/qtforpython-6/PySide6/QtCore/QThread.html),
[pyqtgraph: обновление графиков](https://pyqtgraph.readthedocs.io/en/latest/api_reference/graphicsItems/plotdataitem.html).
